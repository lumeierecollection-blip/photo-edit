# BUILD A COMPLETE GOOGLE DRIVE BATCH PHOTO WATERMARKING SYSTEM

## 1. PROJECT OBJECTIVE

Build a production-ready web application that allows a church media team to batch-process photographs stored inside a Google Drive folder.

The user should only need to:

1. Open the application.
2. Connect/sign in to Google Drive.
3. Paste the Google Drive folder link containing the original photographs.
4. Select/confirm the church logo.
5. Click **"Process Photos."**
6. The system automatically retrieves every supported photograph from that folder.
7. Applies the church logo as a watermark/trademark at the **bottom center** of every photograph.
8. Preserves the original photograph's orientation and dimensions.
9. Preserves image quality as much as technically possible.
10. Creates a new folder in Google Drive for the processed images.
11. Uploads all processed photographs into that new folder.
12. Gives the user a direct link to the newly created Google Drive folder.

The system must be designed for real-world use by a church media team, meaning the interface must be extremely simple and reliable.

The user should NOT need to understand programming, image processing, file formats, APIs, command lines, or technical settings.

# 3. GOOGLE DRIVE INTEGRATION

Use the official Google Drive API and OAuth authentication.

Do NOT ask the user to provide their Google password, Google access token, API key, or credentials manually.

The application should use Google's official OAuth flow.

Required capabilities:

* Sign in with Google.
* Request only the Google Drive permissions genuinely required.
* Read files from the selected source folder.
* Download photographs from that folder.
* Create a new folder in Google Drive.
* Upload processed photographs into that folder.
* Return a clickable link to the created folder.

The application must never delete or modify the original photographs.

The original folder and its contents must remain completely untouched.

# 7. CHURCH LOGO / WATERMARK

The church logo is the watermark.

The logo must support transparency.

Preferred format:

PNG with transparent background.

The application should have a permanent logo configuration.

The administrator should be able to upload/change the church logo from the application's settings.

Do NOT flatten the logo onto a white background.

Transparency must be preserved.

The watermark should be positioned:

HORIZONTALLY:
Exactly centered.

VERTICALLY:
Near the bottom of the photograph with a consistent proportional margin.

Do NOT place it directly against the edge.

Use a proportional margin so the appearance remains consistent across different image resolutions.

For example, conceptually:

bottom margin ≈ 2–4% of image height

The exact value should be configurable.

---

# 8. LOGO SIZE

Do NOT use one fixed pixel size for every photograph.

The logo should scale relative to the photograph.

For example, calculate its width as a percentage of the image width.

The administrator should be able to configure:

* Logo width percentage
* Bottom margin percentage
* Logo opacity
* Optional horizontal offset
* Optional vertical offset

However, create sensible defaults so normal users never need to change these settings.

Example default:

Logo width: approximately 12% of image width
Bottom margin: approximately 3% of image height
Opacity: 100%

Use a maximum and minimum logo size so extremely small or extremely large photographs do not produce ridiculous results.

---

# 9. ORIENTATION HANDLING

This is extremely important.

The application must NOT rotate every image into one standard orientation.

Each photograph must retain the orientation in which it was taken.

Examples:

Landscape:

6000 × 4000

remains:

6000 × 4000

Portrait:

4000 × 6000

remains:

4000 × 6000

Square:

4000 × 4000

remains:

4000 × 4000

The watermark must automatically be centered relative to the final visible photograph.

---

# 10. EXIF ORIENTATION

Many cameras and phones store orientation information inside EXIF metadata rather than physically rotating the pixels.

The application must correctly interpret EXIF orientation.

Before compositing the watermark:

1. Read EXIF orientation.
2. Normalize orientation correctly.
3. Apply the watermark based on the actual visible orientation.
4. Ensure the final exported photograph displays correctly.

Do not produce sideways or upside-down photographs.

Test all standard EXIF orientation cases.

---

# 11. IMAGE QUALITY

Image quality is a major requirement.

The system must NOT unnecessarily resize photographs.

If the original photograph is:

6000 × 4000

the output should remain:

6000 × 4000

unless there is a technical limitation that makes this impossible.

Do not resize images merely to make processing easier.

Do not create thumbnails as the final output.

Do not downscale photographs.

Avoid unnecessary compression.

For JPEG:

* Use high-quality JPEG encoding.
* Make quality configurable.
* Default to a very high quality setting such as 95 or an equivalent visually loss-minimizing setting.
* Preserve chroma quality where supported.

For PNG:

* Preserve PNG quality/losslessness.

For WEBP:

* Preserve dimensions and use high-quality encoding.

For HEIC:

* Preserve dimensions where possible.
* Convert only when necessary.
* If conversion is necessary, clearly document the behavior.

The system should prioritize:

1. Original dimensions
2. Visual quality
3. Correct color
4. Correct orientation
5. Reasonable file size

---

# 12. COLOR MANAGEMENT

Do not accidentally destroy photograph colors.

Handle embedded ICC color profiles where possible.

Avoid converting photographs into an unnecessarily different color space.

The final photograph should visually resemble the original photograph as closely as possible except for the added church logo.

Do not apply:

* Filters
* Sharpening
* Contrast changes
* Saturation changes
* AI enhancement
* Noise reduction
* Automatic color grading

The system is ONLY a watermarking tool.

---

# 13. METADATA

Preserve useful image metadata where technically possible.

Do not unnecessarily strip:

* Camera metadata
* Date/time
* GPS metadata
* Copyright information
* Other useful EXIF information

However, design the application so metadata handling can later be configured by an administrator.

Do not modify metadata unnecessarily.

# 15. DUPLICATE PROTECTION

The application must protect against accidentally creating duplicate processing jobs.

Give the user choices such as:

* Create a new output folder
* Replace/reprocess existing output
* Cancel

Default should be:

Create a new output folder.

Never silently overwrite an existing processed collection.

# 20. RETRY SYSTEM

If an upload or processing operation fails because of a temporary network/API issue:

Automatically retry intelligently.

Use exponential backoff.

Do not endlessly retry.

For example:

Attempt 1
Attempt 2
Attempt 3

After the maximum attempts, mark that photograph as failed and continue.

The user should be able to retry failed photographs afterward.

# 26. WATERMARK COMPOSITING

The watermark algorithm should conceptually be:

1. Load photograph.
2. Read metadata.
3. Correct orientation.
4. Determine final image width and height.
5. Determine logo dimensions proportionally.
6. Resize logo using high-quality interpolation.
7. Calculate horizontal center.
8. Calculate bottom margin.
9. Composite transparent logo onto photograph.
10. Export using appropriate format/quality.
11. Preserve dimensions.
12. Preserve metadata where supported.
13. Verify output.
14. Upload to Google Drive.

The final logo must never extend outside the image.
